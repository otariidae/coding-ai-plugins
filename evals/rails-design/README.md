# rails-design の eval

スキルの各規約が実際に出力を変えているかを見る。
プラグインの配布物には含めない（`plugins/` の外に置いている）。

## 構成

- `evals.json` — テストケース（プロンプト・対象ファイル・アサーション）
- `fixtures/eval-N/` — レビュー対象の架空 Rails コード

実行結果（回答本文・採点・所要時間）は置いていない。再実行すれば作り直せるうえ、
同じ入力でも毎回変わるので、差分が読めなくなる。

## ケース一覧

### eval-1〜6: レスポンスの返し方

`references/controllers.md`「レスポンス」節と、対応するレビューチェックリスト項目の実効性を見る。

| ケース | 機構 | 狙い |
|---|---|---|
| eval-1 `response-definition-scattered` | ハッシュ直書き | 表現定義がコントローラに散っているのを**拾えるか** |
| eval-2 `empty-body-and-error-shape` | ハッシュ直書き | 空ボディ・認可NG・不要な respond_to を**拾えるか** |
| eval-3 `no-false-positive-on-correct-response` | jbuilder partial | 規約どおりのレスポンスを**誤指摘しないか** |
| eval-4 `ams-split-definition` | `active_model_serializers` | serializer を使っている＝1箇所、と**誤判定しないか** |
| eval-5 `jb-template-camelize` | `.json.jb` + `deep_camelize` | jbuilder 以外の機構でも**同じ指摘ができるか** |
| eval-6 `legacy-and-new-serializer` | `JSONAPI::Serializer` → `AMS::JSON` 移行中 | 基底が2つ併存する状態を**拾えるか** |

eval-3 が要。指摘を増やすだけの追記は eval-1/2 だけ見ていると通ってしまう。

### eval-7〜14: 判断フローA–D とレビュー導線

| ケース | 軸 | 狙い |
|---|---|---|
| eval-7 `state-modeling-retired-flag` | 判断フローB | boolean で済ませずレコード化を主案にできるか |
| eval-8 `logic-placement-order-confirmation` | 判断フローA | `app/services` を避け主語モデルへ寄せられるか |
| eval-9 `rest-controller-review` | フローB/C + レビュー導線 | チェックリストを機械的に走査できるか |
| eval-10 `error-handling-payment-timeout` | 判断フローD | 境界での例外翻訳と宣言的リトライに寄せられるか |
| eval-11 `recall-and-factual-accuracy` | レビュー導線 + 正確性 | 渡されたファイルを全部見るか。コードの挙動を誤って説明しないか |
| eval-12 `failure-state-and-swallowed-rescue` | 判断フローD | 握りつぶし rescue と、失敗を表現できないレコードを同時に扱えるか |
| eval-13 `redundant-rescue-and-strategyless-raise` | 判断フローD | 冗長な rescue と受け手のいない raise を整理できるか |
| eval-14 `current-attributes-misuse` | Current | ドメイン状態を Current から出し、引数で渡す形にできるか |

eval-11 に、理由コメント付きで規約から外れている箇所を 3 つ仕込んである。
「コメントがあるから据え置き妥当」と黙って落とすと落ちる。

eval-7〜14 の fixture は、実在のコードベースを調査して頻出パターンを抽出し、
架空ドメインで書き起こしたもの（構造だけ真似ている。実コードは持ち込まない）。

## 分かったこと

### スキルが効く条件

各ケース 3 ラン、実行モデルは Sonnet。ベースラインは
「Skill ツールを使わず自分の知識だけで答える」指示付き。

| ケース | 差 | 素のモデルの答え |
|---|---|---|
| eval-8 ロジックの置き場 | **+77pt**（94% vs 17%） | `app/services` を「Rails で定着した自然な選択」と**積極的に肯定**し、`*Service` を増やす方向に提案する |
| eval-11 レビュー網羅＋正確性 | **+53pt**（100% vs 47%） | 渡された 5 ファイルのうち `routes.rb` と `application_controller.rb` を 3 ラン全部で**無視する** |
| eval-9 レビュー導線 | **+30pt**（89% vs 59%） | `params.expect`・`*Service` の再配置・状態カラムの二重表現を落とす |
| eval-13 冗長 rescue ＋戦略なき raise | **+21pt**（91% vs 70%） | 業務ルール違反を「専用例外クラス化」で解こうとし、型付き例外→独自 Error の 1 対 1 の包み直しを**「お手本」と是認する** |
| eval-7 状態表現 | +11pt（94% vs 83%） | boolean のままカラム追加で済ませる方向に着地しやすい |
| eval-14 Current の誤用 | +8pt（81% vs 72%） | Current がジョブに引き継がれないことは**正しく知っている**。「デフォルト値として参照し引数で上書き」という具体形までは知らない |
| eval-10 エラー設計 | +5pt（90% vs 86%） | `rescue_from StandardError` の否定も `retry_on` / `discard_on` も自力で出せる |
| eval-12 失敗状態＋握りつぶし | +3pt（61% vs 58%） | ほぼ同等 |

数字を読むときの注意が 3 つある。

- **eval-9 は 9 項目版のアサーションで測った数字。** その後 12 項目に増やしたが測り直していない。
- **eval-11 は当初 +61pt と出していた。** 「言及していない」ことを再現率と正確性の 2 つのアサーションで
  二重に減点しており、ベースラインを 8pt 低く見せていた。正確性側を対象外にして再計算した値が上の +53pt。
- **eval-14 は fixture を直す前に測った数字。** 一括取り込みジョブが `created_by` を渡しておらず、
  `belongs_to` の presence 検証で 1 行目の `save!` が落ちるため、プロンプトが言う
  「年度が入っていない仕訳」は**実際には 1 件も作られなかった**。症状が到達不能なまま
  「原因と結びつけられたか」を採点していたので、この数字は前提ごと信用できない。
  fixture は修正済みだが再測定はしていない。

**差の大きさは「素のモデルがどれだけ自信を持って逆を推奨するか」でほぼ決まる。**

- 積極的に間違いを推奨する領域（Service Object、例外機構への寄せ）→ 差が最大
- 網羅性（渡されたファイルを見落とす）→ 差が大きい。チェックリストが機械的走査を強制するため
- 知らないだけ → 差は小さい
- 正しく知っている → 差はゼロ

**「スキルにとって直感と違う判断」＝「モデルにとって直感と違う判断」ではない。**
スキル作者が意外だと思う項目でも、モデルが既に正しく知っていればケースにする価値は無い。
ケースを作る前に、素のモデルが何と答えるかを先に確かめたほうが早い。

### 素のモデルが安定して強い領域（ケースにしない）

- **症状 → 原因の追跡**。プロンプトに症状を書くと、ベースラインは原因コードを正確に特定して
  症状と結びつける。eval-12 と eval-14 の 2 例で確認。eval-14 では該当アサーション 6/6 で満点。
- **コードを読めば分かる構造の問題**。private への切り出しが解決になっていない、
  という構造の話にも到達し、移設先のモデル名・メソッド名まで出せる。

### 採用しなかったケース（コントローラに隠れた業務判断）

`before_action :set_xxx` という定型名に業務判断を隠す形と、判定・計算を private の連鎖に
切り出してコントローラ内にミニドメイン層を作る形を狙った。アクションは全て 5 行程度・
`transaction` 無しにして、チェックリストの「アクションが5行超」「コントローラで transaction」では
捕まらないようにした。

結果は with 100% / without 97%。アサーションを絞って「素直に読めば気づく不整合」を
足し直しても with 71% / without 71% で、2 回とも判別器にならなかった。

**「チェックリストに項目が無いから素通りするはず」という前提が誤り。**
無くてもモデルは自力で見つける。fixture は残していない。

### 両アーム共通の盲点（スキル改善の候補）

- **Current のミュータブルな蓄積**（eval-14）: 6 ラン全滅。全ランが `after_find` には触れるが
  N+1 の性能問題に矮小化し、「属性が処理中に書き換わり際限なく伸びる」という設計論点に到達しない。
- **提案の自己無矛盾性**（eval-14）: 両アームで 1 ランずつ落ちた。
  Current からドメイン状態を除去する提案をしながら、その状態を読むメソッドのデフォルト引数を残す。
  追加した presence バリデーションが、提案自身の 2 段階フローを壊す。
- **提案コードの技術的誤り**（eval-12）: スキル有り 3/3 で誤り。
  enum の bang に引数、integer 列に文字列 enum、セクション間で設計が矛盾。
- **見落としたバグを提案でも直さない**（eval-14）: 指摘しないだけでなく、修正後のコード例でも同じ欠陥を残す。

## アサーションの層

層ごとに通り具合を見ると、どこで失敗しているかが切り分けられる。

| 層 | 測るもの |
|---|---|
| A 検出 | 問題に気づくか |
| B 提案 | どこに移すか具体的な置き場を示せるか |
| C 妥当性 | 提案がコードと整合し、Rails の API として成立し、**自己無矛盾か** |
| D 実バグ | 入力に実在する欠陥を、症状と結びつけて指摘できるか |
| 適合率 | 直さなくてよいものを直せと言っていないか |

A が満点で B が落ちれば「気づくが直せない」、B が通って C が落ちれば
「それっぽい提案をするが適用すると壊れる」と切り分けられる。後者は実際に起きた。

## 回し方

`anthropic-skills:skill-creator` の手順に従う。各ケースにつき2エージェント
（変更後のスキル / 変更前のスナップショット、またはスキル無し）を同一ターンで起動し、
レビュー本文を `<workspace>/iteration-N/eval-*/{with_skill,without_skill}/outputs/response.md`
に保存させる。スナップショットは `git archive <前の SHA> plugins/rails-design/skills/rails-design` で作る。

`eval_metadata.json` は `evals.json` から生成する:

```bash
jq --argjson id 7 '.evals[] | select(.id == $id) | {eval_id: .id, eval_name: .name, prompt, assertions}' evals.json
```

採点は skill-creator の `agents/grader.md`、集計は `scripts.aggregate_benchmark`、
閲覧は `eval-viewer/generate_review.py` を使う。

ベースラインには「Skill ツールを一切使わず、自分の知識だけで答えること」を明示する。
プラグインとして環境にインストールされていると、指示が無ければ参照しうる。

## 測定上の教訓

- **サブエージェントの完了サマリを数字の根拠にしない。** 実ファイルを読んだ採点結果と
  ズレることが 2 回あった（検出率を 3/3 と誤報告→実際は 1/3 など）。
- **非弁別的なアサーションは削る。** 両アーム全通しの項目は集計を薄めるだけ。
  ただし退行検知には使えるので、差がついた項目と分けて読む。
- **誰も検出できないアサーションも削る。** 6 ラン中 0 件なら、そもそも欠陥と言い切れるか怪しい。
  例外として eval-14 の `Current#touch_account` は 6 ラン全滅のまま残している。
  これは弁別のためではなく、両アーム共通の盲点を追うための目印として置いている。
- **fixture の前提が成立しているかを確かめる。** プロンプトに書いた症状が、その fixture で
  実際に起きうるかは別問題になる。eval-14 では `belongs_to` の presence 検証が先に落ちて
  症状に到達しないまま、6 ラン全部が「正しく診断した」と採点されていた。
  レビュー時に指摘されるまで気づかなかった。
- **消極的パスに注意。** 「〜と誤って述べていない」だけの否定形は、そのファイルに一度も
  触れていない回答が自動的に通る。言及自体を問う正のアサーションを前段に置く。
- **スキルに不利な方向のアサーションも入れる。** 実力差があるのに測れていない項目を足したところ、
  差が +10pt → +8pt に縮んだ。縮むこと自体が正しい測定。
- **出力は使い回せる。** アサーションだけ変えるなら再実行は不要で再採点のみ。
  ベースラインはスキル非依存なので、スキルを変えても流用できる。

## 初回（レスポンス節の追記時）に分かったこと

**アサーションのほとんどが非差別的だった。** 追記前のスキルでも、eval-2 は5項目すべて、
eval-1 は4項目中3項目を拾った。eval-3 は追記の有無にかかわらず誤指摘ゼロ。
`head :no_content` / `head :forbidden` / 不要な `respond_to` / `success: true` を捨てる、
といった指摘は書かなくても出る。

差がついたのは2点だけ:

- **キー変換の散らばり** — 追記前は表現の話のついでに括弧書きで触れるだけ。追記後は独立した指摘になった
- **エラー形式を1つに決める** — 追記前は言及なし

そのため初稿の40行は12行に削った。残すのはこの2点と、両者の前提になる
「表現の定義は1箇所」だけ。**素のモデルが出せる指摘を書いても、長さが増えるだけで出力は変わらない。**

## 機構を変えても効くか（eval-4〜6）

3ケースとも全アサーション該当。機構に合わせた具体案まで出た
（AMS なら `render json: @lesson, serializer:` に寄せる、jb ならレンダラ側で
`deep_camelize` を1回だけ通しテンプレートは snake のまま、など）。
「serializer を使っているから表現は1箇所」という誤判定も起きていない。

**規約を機構非依存に書いた判断はここで裏が取れた。** 逆に、初稿のように jbuilder の
コード例を厚く書いていたら、jb や AMS のコードに当てたとき「機構が違う」で流れた可能性がある。

副産物として、仕込んでいない問題も拾った（eval-4 の認可漏れ、eval-5 の
partial 二重エンコード疑い）。fixture は機構の再現だけを狙って書いたので、
これらは意図しない現実味であって、アサーションには入れていない。

eval-7〜14 でも同じことが起きている。fixture を書いたときに気づいていなかった不整合を
両アームが拾った（パラメータ取得元のねじれ、到達不能なガード、NOT NULL 制約違反など）。
見つかった実在の問題はアサーションに追加し、誤検知として扱わないよう注記している。
